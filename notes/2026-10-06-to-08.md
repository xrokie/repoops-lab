## 10 月 6 日：等待时，让别的任务继续

### 从原来的执行器看起

`src/executor.py` 中的 `Job` 保存一个任务的编号、函数、状态、结果、错误和时间。`JobExecutor.run()` 直接执行 `job.task()`，等它返回后，调用者才能继续。

例如三个任务各等待服务器一秒，依次执行会等待约三秒。异步版本让它们在等待服务器期间交替推进，总耗时可能接近一秒。这是把等待时间重叠，并不意味着一个处理器同时做三份计算。

### async、await、Task 各自做什么

`src/async_executor.py` 的 `AsyncJobExecutor.run()` 使用 `async def` 定义，表示它可以暂停并在稍后继续。单独调用这个函数只得到一个待运行的对象，还要用 `await` 等待它，或者交给 `asyncio.create_task()` 安排运行。

```python
job.result = await job.task()
```

`await` 表示等待另一个异步操作完成。当操作尚未完成、确实需要等待时，当前任务交出执行机会，别的任务就可以运行。不是每个 `await` 都一定发生切换。

Task 是已交给异步调度器管理的任务对象，能查看是否结束，也能申请取消。演示入口 `examples/learning_demo.py` 最后用 `asyncio.run(main())` 启动整个调度过程。

### Queue：等待处理的编号

`run_all()` 把任务编号放进 `asyncio.Queue`，随后建立若干处理循环，每个循环取一个编号，执行完再取下一个。这样有一百个任务、并发上限为三时，不必一次启动一百个任务函数。

本版是在运行一批任务前就填好队列，所以取不到编号时可以结束。如果改成持续接收新任务的服务，队列暂时为空不代表全部工作完成，应使用等待取出、明确的停止信号等办法。

### Semaphore：同时最多允许几个任务执行

构造函数建立 `asyncio.Semaphore(max_concurrency)`，可理解成有限数量的通行证。

```python
async with self._slots:
    job.started_at = utc_now()
    job.transition_to(JobStatus.RUNNING, occurred_at=job.started_at)
```

取得通行证后才进入运行状态；没有通行证的任务继续等待。任务结束或发生错误时，`async with` 自动归还通行证。队列决定下一步处理谁，通行证限制当前同时运行多少个任务。两个功能不同。

### TaskGroup：一批处理循环的共同负责人

`run_all()` 用 `asyncio.TaskGroup` 管理处理循环。正常退出这个范围时，内部任务都已结束；外层取消时，它会取消内部任务并等待清理结束。

任务函数的一般错误由 `_run()` 记录为失败，其他任务仍继续。若处理循环本身出现没有接住的错误，任务组会停止其他处理循环并向上报告错误。两种情形不要混淆。[Python 任务组与取消说明](https://docs.python.org/3.13/library/asyncio-task.html)

### 取消和超时为什么要有不同状态

任务状态现在允许：

```text
等待 → 运行 → 成功 / 失败 / 取消 / 超时
等待 → 取消
```

取消表示调用者要求停止；超时表示超过规定时间。失败表示任务尝试执行，但遇到了错误。分开记录后，才能判断应该修参数、调整时间限制，还是接受用户主动停止的结果。

`_run()` 接到 `CancelledError` 后先记录取消，再用 `raise` 继续传递。取消通知不能随意吃掉，否则外层可能以为任务正常完成。

```python
except asyncio.CancelledError as exc:
    self._finish(job, JobStatus.CANCELLED, exc)
    raise
```

任务函数应把清理工作放在 `finally` 中。取消不是立即强行掐断计算，而是在任务下次有机会暂停时发出通知。`while True: pass` 不会暂停，会卡住整个异步调度过程；10 月 7 日的容器负责停止这类命令。

`asyncio.timeout()` 为执行阶段设置时限，排队时间不计入本版的执行超时。任务自己抛出的 `TimeoutError` 会记作失败，只有本次时限真正到期才记作超时。

### 网络的四种等待

`src/retry_policy.py` 的 `RetryPolicy.timeout()` 分别设置：

| 参数 | 等什么 | 默认秒数 |
| --- | --- | --- |
| connect | 建立网络连接 | 3 |
| read | 收到下一块响应数据 | 10 |
| write | 发送下一块请求数据 | 10 |
| pool | 从可重复使用的连接中取得一个空闲连接 | 3 |

读取超时是等一块数据的时间，不是整个请求的总时长。一个持续缓慢发送数据的服务器可能始终没有触发读取超时；总时间限制可以由外层执行器提供。[HTTPX 超时说明](https://www.python-httpx.org/advanced/timeouts/)

### 什么时候重试

本版最多尝试三次，首次也算一次。暂时的网络错误和 429、502、503、504 可以在请求安全的前提下重试；400、401、403、404、422 等直接报告失败。证书验证失败也不重试，需要修复证书或连接配置。500 的原因跨度很大，本版保守地直接失败，不代表所有接口的 500 都永久不能重试。

状态码的意思：429 是访问过于频繁；502、503、504 常涉及上游服务暂时出问题；400 是请求不对；401、403 涉及身份或权限；404 是资源不存在；422 是内容不符合接口要求。

等待时间逐次增长，默认约为 0.25、0.5 秒，再加一点随机时间。这叫退避：服务正忙时，避免每个客户端同时立即再来一遍。服务器返回 `Retry-After` 时遵守它；要求等待超过本版上限就结束，不能擅自把两分钟缩成十秒后继续访问。

### 重试为什么可能重复写入

你请求“创建一个任务”，服务器已经创建成功，但回包在路上丢了。你只看到超时；再次请求可能创建第二个任务。

这就是“没有收到成功消息”不等于“对方没有执行”。读取请求默认允许重试；写入请求只有提供固定的 `idempotency_key`，并明确确认服务端支持按这个编号去重，才允许重试。这个编号叫幂等键，意思是相同请求重复发送时仍对应同一次操作。

本版的 `server_deduplicates=True` 是调用者对接口能力的确认，不能凭空给服务器增加去重能力。所有重试沿用同一个编号，而不是每次换新编号。请求内容也应保持一致；不要拿不能重新读取的数据流作为可重试请求体。

### 用例子检验理解

运行 `examples/learning_demo.py` 会看到三个请求的第一次尝试先出现，随后两个暂时失败的请求各自重试。参数错误的请求只出现一次。

测试在 `tests/test_async_executor.py` 和 `tests/test_retry_policy.py`。重点看：三个任务真正重叠、同时运行人数不超限、整批取消后没有剩余任务、单个取消不丢弃队列，以及写入请求不能仅凭一个请求编号就自动重试。

## 10 月 7 日：让卡死的命令有边界

### Docker 容器是什么

容器是一个隔开的运行环境，拥有自己的进程和文件视图。Docker 负责创建和管理它。镜像是这个环境的启动材料，`Dockerfile` 描述里面安装什么软件、放什么文件。

在本项目中，Dockerfile 安装 Python 测试工具，再把 `src`、`tests` 和项目配置复制进去。之后容器内运行测试，不依赖宿主电脑上临时安装了哪些 Python 包。

Mac 上 Docker Desktop 在 Linux 虚拟机中运行这些容器，容器并不是直接共用 macOS 内核的进程。

### 对照 sandbox_runner.py 看执行顺序

```text
创建容器 → 启动 → 等待结束 → 查看真实状态 → 收集日志 → 删除容器
                     ↓ 超时或取消
                  停止容器，再收集和删除
```

`SandboxRunner.run()` 执行这条流程。命令通过参数列表传给系统，没有把它拼成一条自动解释的命令字符串。

仅停止本地 `docker wait` 程序不会停止容器里面的任务，因此超时后还要调用 `docker kill`。最后的 `finally` 无论成功、失败还是取消，都尝试删除这次创建的容器；`container_removed` 记录是否真的清理成功。

### 限制是逐项设置的

`create_args()` 中的配置：

| 限制 | 当前值 | 实际含义 |
| --- | --- | --- |
| CPU | 0.5 | 最多约半个处理器核心的计算份额 |
| 内存 | 128 MB | 超过限制可能被系统杀掉 |
| 进程和线程数量 | 32 | 防止不断创建新进程或线程 |
| 网络 | 关闭 | 容器命令不能访问外网 |
| 程序目录 | 只读 | 不能改写镜像内的程序文件 |
| 临时目录 | 16 MB | 只在容器内临时写入，删除后消失 |
| 宿主目录挂载 | 没有 | 容器没有直接写入本仓库目录的通道 |

此外使用普通用户运行、移除额外系统权限，并限制日志文件大小。CPU 限制主要让计算变慢，时间限制才负责结束无限循环。容器是一种执行边界，这份学习实现不等于完整的多人远程代码运行服务。[Docker 资源限制说明](https://docs.docker.com/engine/containers/resource_constraints/)

### 不能只看退出码

退出码 0 通常表示命令自己报告成功；非零表示没有正常成功。但 137 不能单独证明内存耗尽，因为主动强制结束也可能得到这个数字。

`_collect()` 查看 Docker 的 `OOMKilled` 标记。OOM 是内存耗尽的缩写。只有这个标记为真才归类为内存耗尽；超时和主动取消则保留它们自己的原因。

容器结果有成功、命令失败、超时、取消、内存耗尽、执行环境错误六类。环境错误包括 Docker 不可用、镜像不存在、状态读取失败或清理失败。返回一个结果对象不等于容器中的命令成功，调用者必须检查 `result.status`。

### 故意破坏，再检查结果

`tests/test_sandbox_runner.py` 的真实容器测试会：

1. 在容器内运行仓库测试。
2. 让程序主动以非零退出码结束。
3. 运行无限循环，检查超时后停止。
4. 不断申请内存，检查内存耗尽的真实标记。
5. 尝试写入只读目录，检查是否被拒绝。
6. 不断创建子进程，检查数量限制，并等待子进程结束。
7. 在容器启动后取消任务，检查容器已删除。

普通测试中的 FakeDocker 只是模拟 Docker 返回值，检验判断和清理分支。真实测试明确单列，只有实际启动容器后才算容器验证。

## 10 月 8 日：机器人看见、理解、动作、再观察

今天计划里的 VLA 是视觉、语言、动作模型：把相机画面、文字任务和机器人当前状态一起输入，输出动作。SmolVLA 是这一类模型中的一种；LeRobot 提供数据格式和训练、执行、评测工具；LIBERO 是一组用于检验机器人操作能力的模拟任务。[SmolVLA 官方说明](https://huggingface.co/docs/lerobot/smolvla)

RepoOps 目前没有机器人模型代码。任务执行器管理“这次评测是否跑完”；机器人模型决定“手臂下一步怎么动”。因此本节直接讲知识。

### 观察是什么

观察包括相机画面和机器人自身状态。以 LIBERO 为例，输入包含主相机、腕部相机，以及末端位置、朝向、夹爪等状态。仅有文字“把杯子放到盘子上”并不能告诉模型杯子此刻在哪。

### 文字怎样进入模型

文字会先拆成模型词表中的小单位，再转成数字编号，这个步骤叫分词。图像也会变成可供模型处理的特征，机器人状态需要按训练时约定的方式缩放。

不要据此认为所有 VLA 都把动作也转成离散词。SmolVLA 的动作部分生成连续数值，并能一次预测一小段动作。动作表示和文字分词是不同问题。

### 动作是什么

动作是一组数值，例如让机械臂末端沿三个方向移动多少、朝向怎样改变、夹爪开还是合。LIBERO 的默认动作有七个数：六个描述末端位置和朝向变化，一个控制夹爪。[LIBERO 输入与动作说明](https://huggingface.co/docs/lerobot/libero)

相对动作表示“从当前位置再移动一点”；绝对动作表示“移动到指定目标”。模型训练时的动作约定必须与模拟环境一致。毫米、米或归一化后的数值也不能直接混用。

### 控制为什么要循环

```text
相机和传感器观察 → 模型产生动作 → 环境执行动作 → 取得新观察 → 再决策
```

一次抓取可能没抓住，物体也可能移动。重新观察才知道前一次动作造成了什么结果。一次预测一段动作可以减少调用次数，但执行太长的一段后才重新观察，会增加对环境变化反应迟缓的风险。

### 训练数据与评测数据各有什么用

训练数据包含示范：某个画面和任务下，人或已有策略执行了什么动作。模型从这些对应关系中学习。

评测则在环境里真正执行：模型观察、输出动作、环境变化，直到成功、失败或时间用完。只检查模型能不能输出一个七维数组，不算完成机器人评测。

### 最小评测该固定什么

先选一个任务、一个适配它的模型版本和固定的随机种子。种子控制一部分随机过程，方便重复实验；它不保证不同硬件下的每个数值都完全一致。

记录每轮是否成功、执行步数、耗时、种子、模型版本、环境版本及日志与失败录像。先用少量轮次确认运行，再增加重复次数观察稳定性。基线就是后续修改要对照的原始表现。

官方当前的一个任务入口示例如下；运行前需要在支持的 Linux 环境安装 LeRobot、SmolVLA 与 LIBERO，并确认所选模型的输入、动作和归一化配置匹配：

```sh
lerobot-eval \
  --policy.path=HuggingFaceVLA/smolvla_libero \
  --env.type=libero \
  --env.task=libero_spatial \
  --env.task_ids='[0]' \
  --seed=42 \
  --eval.batch_size=1 \
  --eval.n_episodes=3 \
  --env.max_parallel_tasks=1
```

这是参考入口，未在本机执行或证明与所下载模型版本兼容，不能把它算作实测结果。本机是 macOS，当前未安装 torch、lerobot、mujoco、libero；官方 LeRobot 的 LIBERO 集成要求 Linux。10 月 8 日的真实模型评测、逐任务成功率和失败录像仍未完成。[LIBERO 安装与评测说明](https://huggingface.co/docs/lerobot/libero)
